# База знаний: стратегия тестирования

## Цель

Тестовый набор должен быть типобезопасным, воспроизводимым и полезным при
рефакторинге. Целевой результат — не менее 90% line coverage прикладного кода
при полностью зелёном запуске тестов. Покрытие измеряется только после
устранения ошибок collection; миграции и тестовый код остаются исключениями,
но прикладные модули нельзя исключать ради метрики.

## Что считаем основой качества

1. Основная ценность — функционально-интеграционные проверки API: HTTP-запрос
   проходит через реальные маршруты, middleware, валидацию, зависимости,
   UoW/repositories и PostgreSQL.
2. В API-тесте проверяются контракт ответа, коды ошибок, права доступа и
   состояние, сохранённое в БД. Он не проверяет внутренние вызовы репозиториев
   или конкретную последовательность реализации.
3. Сервисы, repositories, UoW, токены и сложная обработка ошибок получают
   отдельные unit- и около-интеграционные тесты. Здесь допустимы строгие mocks
   для проверки взаимодействий.
4. Вьюхи тестируются без рендера HTML: прямой вызов контроллера должен
   проверить имя шаблона и полный переданный `context`.

## Структура и стиль

- Тесты группируются классами по публичному поведению:
  `TestPodcastApi`, `TestEpisodeApi`, `TestAuthApi`, `TestPodcastView`.
- Имя теста описывает наблюдаемое правило, например
  `test_list_returns_only_current_users_podcasts`.
- Параметризация используется для вариантов одного контракта: невалидные
  payload, роли, статусы и пограничные значения.
- Общие проверки HTTP-конверта и ошибок живут в типизированных assertion
  helpers, а не копируются в каждом тесте.
- Новые тесты должны иметь точные типы параметров и результатов. По завершении
  миграции `../../src/tests` проверяется mypy и больше не исключается из него.

## Данные и изоляция

- Функциональные тесты используют выделенную PostgreSQL-базу, никогда не
  локальную или рабочую базу разработчика.
- Схема подготавливается один раз за тестовую сессию. Перед каждым
  функциональным тестом данные очищаются надёжным способом; тесты не зависят
  от порядка запуска и не делят доменные данные.
- Доменные fixtures имеют `function` scope по умолчанию: `user`, `other_user`,
  `podcast`, `episode`, `audio_file`, `image_file`, `cookie`, `user_session`.
  Они создают реальные, согласованные записи в БД и возвращают конкретные
  типы моделей.
- `session` scope разрешён для инфраструктуры: тестовой БД, схемы, миграций,
  конфигурации и неизменяемых бинарных образцов. `module` scope — только для
  тяжёлых неизменяемых данных; не для изменяемых сущностей.
- Fixture-фабрики принимают осмысленные override-параметры, чтобы сценарий
  оставался читаемым и не собирал модели вручную.

## Внешние границы и заглушки

- PostgreSQL остаётся реальной. S3, Redis, RQ, SMTP, HTTP-клиенты, yt-dlp и
  ffmpeg не требуют сети или отдельных сервисов в обычном тесте.
- Для классов внешних границ создаётся stateful `BaseMock` с заранее
  определённым поведением и историей вызовов. Function-scoped fixture патчит
  конструктор и явно перечисленные методы production-класса, возвращая fake
  тесту для assertions и полностью восстанавливая класс после теста.
- Module-level функции SMTP, media source и ffmpeg патчатся методами
  соответствующих stateful fakes. Подмена устанавливается в модуле, где символ
  используется, либо на общем module object, если production-код обращается к
  нему через module import.
- Общими для app/client fixtures остаются только безопасные lifecycle- и
  RQ-подмены. S3, Redis, SMTP и media fixtures подключаются явно в сценариях,
  которым они нужны.
- Для unit-проверок взаимодействий используются `AsyncMock(spec=...)` или
  `create_autospec(..., spec_set=True)`, а не неограниченные `Mock`, `Any` или
  `SimpleNamespace`.
- Функциональный тест проверяет наблюдаемый побочный эффект fake-границы
  (например, поставленную задачу или путь загрузки), а не детали внутренней
  проводки объектов.

## Dependency boundaries

- Production application factory не принимает test providers и не хранит
  service locator. `PodcastApp` напрямую собирает очередь, а контроллеры и
  сервисы используют обычные production constructors/functions.
- Functional tests направляют все `SASessionUOW()` в тестовую PostgreSQL через
  одну подмену `db.session.get_session_factory`. Это не требует добавлять
  test-only параметры в UoW, контроллеры или auth backend.
- Litestar DI используется для естественных request-зависимостей, например
  settings и current user. Локальная constructor injection допустима внутри
  самостоятельного сервиса, если является частью его рабочего контракта, а не
  существует только ради application fixture.
- Monkeypatch устанавливается на минимальной внешней границе и живёт только в
  пределах fixture. Тест не патчит repositories в функциональном API-сценарии
  и не обходит реальные маршруты, middleware или PostgreSQL.

## Минимальный сценарий для новой API-операции

1. Успешный путь с проверкой ответа и записи в БД.
2. Недоступность чужой сущности.
3. Невалидный запрос и договорённый формат ошибки.
4. Важные переходы состояния и идемпотентность, если они есть.
5. Проверка внешнего побочного эффекта через fake, если операция его создаёт.

## Запрещённые shortcuts

- Не выдавать mock repository за функциональный API-тест.
- Не делить записи БД между тестами и не полагаться на порядок запуска.
- Не вызывать реальную сеть, S3, Redis или RQ из обычного теста.
- Не повышать покрытие пустыми assertions, широкими исключениями или новыми
  исключениями из coverage.
- Не рендерить шаблон ради проверки контекста.
