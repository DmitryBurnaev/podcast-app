# Внедрение htmx + Alpine и перенос возможностей прежнего Vue-интерфейса

Дата: 2026-10-16. Статус: согласованное направление, реализация не начата.

План основан на текущем `podcast-app` и исследовании прежнего Vue-приложения,
скопированного в `../../.local/podcast-ui`. Переносим полезные сценарии и поведение,
сохраняя текущий серверный рендеринг и лёгкий фронтенд.

## 1. Принятые решения и границы

- Litestar + Jinja остаются основой приложения и источником HTML.
- htmx отвечает за серверную динамику: формы, списки, фильтры и обновление фрагментов.
- Alpine отвечает за локальное состояние: диалоги, меню, плеер, главы,
  выбор элементов, очереди импорта и загрузки.
- JSON и multipart запросы допустимы там, где удобнее управлять операцией из Alpine.
  Для них сохраняется небольшой общий HTTP-клиент.
- Объём полный, но поэтапный: текущие экраны, плейлисты, загрузка файлов,
  обложки, главы, профиль и регистрация по приглашению.
- Без сборки фронтенда: локально поставляемые htmx и Alpine с закреплёнными
  версиями, обычные JS-файлы. Node.js не требуется для production-сборки.
- Не переносим Vue, Vuex, Vue Router, Axios, Element UI, Bootstrap и плагины
  прежнего приложения. Сохраняем текущий дизайн.
- Плеер живёт в пределах страницы. Обновление фрагментов на этой странице
  сохраняет воспроизведение; обычный переход на другую страницу его останавливает.
- Обложки: загрузка и превью, без обрезки изображения.
- Прогресс: единый polling, без WebSocket/SSE на этом этапе.
- Авторизация веб-интерфейса остаётся на session cookie. Публичный `/api/*`
  с bearer-авторизацией сохраняет совместимость.
- Автоматизированные тесты в рамках миграции — только pytest:
  API, контекст/шаблон view и Python unit-тесты. Отдельные frontend-тесты не добавляем.

## 2. Обязательный порядок каждой итерации

Эти требования применяются к каждому этапу ниже. Большой этап можно разбить
на несколько законченных итераций; проверки обязательны для каждой из них.

1. Зафиксировать конкретный объём итерации и сценарии приёмки.
2. Внести изменения, сохраняя работоспособность остальных экранов.
3. Добавить или обновить необходимые pytest-тесты по правилам
   `../testing/knowledge-base.md`: API, контекст view, Python unit-тесты.
4. Прогнать релевантные pytest-тесты и регрессионные проверки затронутых сценариев.
   Перед завершением всей миграции прогнать полный pytest-набор.
5. Проверить результат во встроенном браузере: изменённые сценарии,
   их ошибки и затронутую существующую функциональность. Для адаптивных
   компонентов дополнительно проверить узкий viewport.
6. Зафиксировать команды, результаты pytest, проверенные браузерные сценарии,
   обнаруженные ограничения и оставшиеся проверки.
7. Подготовить развёрнутый commit message в стиле актуальной истории репозитория:
   что изменено, зачем, как изменилось поведение, какие проверки выполнены
   и какие существенные ограничения остаются. Сообщение составляется по
   фактическому diff после проверок.
8. Обновить статус итерации в этом документе. Изменять
   `../testing/plan.md` только при фактическом выполнении или изменении
   соответствующих пунктов миграции тестов.

Итерация не считается завершённой при падающих проверках или отсутствии
проверки во встроенном браузере. Если браузер недоступен, это незавершённая
проверка, которую нужно явно записать и выполнить позже.

Pytest и браузерная проверка дополняют друг друга: серверные тесты проверяют
контракты и бизнес-правила, браузер — реальную интеграцию htmx/Alpine и DOM.
Они снижают риск регрессий, но не являются доказательством отсутствия всех ошибок.
Отдельный JS unit/e2e runner в план не входит. Подготовка этого документа
не предполагает удаления уже существующих frontend-тестов.

Статические проверки проекта выполняются по необходимости. Каждая команда
lint/test запускается отдельно. Для pytest использовать `/opt/homebrew/bin/uv`
с `UV_CACHE_DIR=/private/tmp/codex-uv-cache` и согласованное тестовое окружение.

Подготовка commit message не означает автоматический commit или push:
публикация и git-операции согласуются отдельно в рамках соответствующей задачи.

## 3. Распределение ответственности

| Уровень | Ответственность |
| --- | --- |
| Jinja + htmx | Списки, поиск, фильтры, пагинация, обычные CRUD-формы, HTML-фрагменты |
| Alpine | Диалоги, мобильное меню, локальные состояния, плеер, главы, импорт и загрузка |
| HTTP-клиент | JSON/multipart, credentials, timeout/abort, нормализация ошибок |
| Координатор страницы | Polling, координация мутаций и обновлений, защита от устаревших ответов |
| Серверные сервисы | Общие операции для публичного API, web JSON и HTML-контроллеров |

Компоненты оформлять через `Alpine.data` в отдельных JS-файлах. В шаблонах
оставлять короткие привязки и декларативную разметку, не большие программы.

Правила взаимодействия:

- У каждой операции один отправитель: htmx либо Alpine. Не запускать оба
  обработчика для одной формы или кнопки.
- У каждой DOM-области один владелец. Фоновое обновление не заменяет редактируемую
  форму, плеер или активную очередь загрузки.
- Общие события: `podcast-changed`, `episode-changed`, `rss-generated`,
  `profile-changed`. Передавать идентификаторы затронутых сущностей.
  Для ответов htmx использовать `HX-Trigger`/`HX-Trigger-After-Swap`
  в соответствии с нужным моментом обработки.
- Polling один на страницу: базово 2 секунды, backoff до 30 секунд,
  пауза в скрытой вкладке и остановка при 401. Не создавать таймер на карточку.
- Координатор откладывает конфликтующие фоновые обновления на время мутаций.
  Ответы для прежнего URL, фильтра или поколения запроса не применяются.
- При уничтожении компонента очищать таймеры, обработчики, запросы и object URL.
- Начать с адресных обычных swaps. Отдельную morph-зависимость не вводить
  без доказанной потребности.

## 4. Серверные контракты и совместимость

### HTML

- Сохранить URL полноценных страниц. Добавить внутренние `/ui/*` обработчики
  форм и фрагментов с session cookie; названия ресурсов и действий согласовать
  с существующими контроллерами.
- Формы передают стандартные form/multipart данные.
- Успешный ответ возвращает HTML либо 204 с событием обновления.
- Ошибки валидации возвращают 400 и HTML ошибок. Явно настроить ограниченный
  swap для этих ответов, сохраняя введённые значения.
- 401 показывает сообщение об истёкшей сессии и переход к входу;
  страница логина не должна попадать внутрь карточки или формы.
- Единообразно обработать 403, 404, 409 и сетевые ошибки. После timeout мутации
  не делать автоматический повтор без выяснения её результата.
- Сохранить текущую проверку Origin и `X-Requested-With` для мутаций;
  заголовок для htmx задавать централизованно.
- При различии ответа по `HX-Request` выставлять соответствующий `Vary`.
  Совместимость `?fragment=1` сохранять до переноса последнего потребителя.

### JSON и общие операции

- Расширять session JSON `/web-api/*` для предпросмотра плейлиста,
  загрузки аудио/изображений, создания эпизода из файла, обложки подкаста
  и создания токена с однократным показом его значения.
- Повторно использовать существующие бизнес-правила публичного API.
  Если они находятся в контроллере, выделять общий сервис, а не вызывать
  один контроллер из другого и не делать HTTP-запрос приложения к самому себе.
- Особое внимание общим сервисам media, playlist, cookies и profile.
- Сохранить проверки владельца и доступа во всех новых веб-обработчиках.
- Согласовать DTO с текущим сервером: прямые ответы без старого `payload`,
  пагинация `items/offset/total`, актуальный alias `sourceURL`.

Важные отличия от прежнего Vue-клиента:

- Текущий `get_uploaded` возвращает метаданные файла (`UploadedEpisodeResponse`),
  а не созданный эпизод. Нельзя трактовать ID файла как ID эпизода.
  Для дедупликации предусмотреть отдельный поиск эпизода по hash в рамках
  конкретного подкаста и владельца: `EpisodeResponse` либо 404.
- При создании эпизода по URL сервер уже блокирует подкаст и проверяет дубли.
  Для создания из загруженного файла также обеспечить серверную сериализацию
  в рамках подкаста: последовательность в UI сама по себе недостаточна.
- Ошибка очереди может произойти после создания эпизода. Учитывать
  `503` с `details.episode_id`, чтобы повтор не создавал дубликат.
- Для IP использовать текущие `hashed_address`, `registered_by`, `created_at`;
  не обещать сырые адреса и связи со старым RSS, которых нет в текущем контракте.
- Значение нового токена возвращается один раз; последующие списки содержат
  только метаданные.
- Для глав использовать серверную нормализацию start/end в секунды,
  а не повторять парсинг старого клиента.

## 6. Регрессионные сценарии

Выбирать относящиеся к итерации сценарии; полный проход обязателен в конце.

- CRUD подкаста/эпизода, ошибки полей, отмена подтверждения, двойное нажатие.
- Поиск, фильтры, Back/Forward, дозагрузка и медленные ответы прежнего запроса.
- Запуск/отмена скачивания, прогресс, RSS, согласованность списков и счётчиков.
- Polling при открытой форме/диалоге, скрытая вкладка, 401, сетевой сбой и backoff.

- Частичная загрузка файлов, выбранные строки, метаданные, массовые изменения,

внешние сервисы, шаблон и контекст view без HTML snapshots, unit-тесты
нормализации и выделенной логики согласно knowledge base.
